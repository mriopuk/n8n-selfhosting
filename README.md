## 自托管 n8n 到底在解决什么问题

n8n 用节点连线的方式把不同系统串起来：定时拉某个接口的数据写进表格、表单提交后自动建工单并通知、Webhook 收到回调做转换再转发。它采用 fair-code 许可，可以装在自己的服务器上，不按执行次数计费。

选择自托管而不是用官方托管服务，理由一般就三条：处理的数据不方便经过第三方、需要访问内网系统、工作流执行量大想控制成本。

得说清楚边界。n8n 擅长的是流程编排，不适合扛高并发的实时数据处理。单实例的默认部署方式够中小规模用；真到了每天几十万次执行，得额外上队列模式和多副本，那是另一个话题了。

## 服务器配置：官方给的参考和实际吃资源的差距

| 项目 | 最低配置 | 建议配置 |
| --- | --- | --- |
| CPU | 1 核 | 2 核及以上 |
| 内存 | 1 GB | 2～4 GB |
| 磁盘 | 20 GB | 40 GB 以上 |

社区和官方文档的口径基本一致：1 vCPU + 2GB 能跑起来，2 vCPU + 4GB 以上更适合长期生产使用。

但这个表只能当起点。真正吃内存的是工作流本身——一个把几万行数据读进内存做聚合的节点，和发一条通知的节点，占用完全不在一个量级。如果你打算在 n8n 里跑 AI 节点、处理大文件，或者同时挂十几个定时任务，2核4G 会显得紧。

磁盘同理。除了系统盘，执行历史会一直往里堆。默认保留策略下，长期运行的实例占到十几 GB 很正常，另外还得留出 Docker 镜像和 Postgres 数据的空间。

数据库这块建议一开始就想清楚：

- **SQLite**：n8n 默认选项，零配置，个人用、工作流不多完全够。
- **PostgreSQL**：并发写入更稳，多人协作和长期运行推荐。中途从 SQLite 迁到 Postgres 需要额外导数据，不如一开始就定下来。

## 机器放哪儿：国内节点、香港节点、海外节点的实际差别

这个问题比配置更容易被忽略，但它决定了你后面能不能顺利上线。

要判断的其实就三件事：

**一、域名要不要备案。** 自托管 n8n 想正常用，基本都得配一个域名并上 HTTPS——Webhook 地址、OAuth 回调地址都要求是公网可达的 HTTPS。国内节点绑域名需要走备案流程，香港和美国节点免备案，解析完 A 记录就能直接签发证书。雨云官方说明里，洛杉矶一区/二区、香港二区/三区属于免备案区域。想当天就把 n8n 跑起来，这几个区域省事得多。

**二、拉镜像的速度。** 部署过程要拉 Docker 镜像和系统依赖。国内节点通常最快，香港次之，美国和德国节点在高峰期可能慢一些，但也就多等几分钟，不是决定性因素。

**三、要连的内网系统在哪。** 这条才是关键。大多数自动化场景对接的是飞书、钉钉、企业微信、Notion、Google Sheets 这类公网 API，节点放在哪个区域只影响延迟和带宽。但如果你的流程要读写公司内网的 MySQL 或者 ERP，那机器就得放在能打通内网的位置，这一步从选区域开始就得定。

如果你对延迟比较在意，雨云同一区域往往分「大带宽限流量」和「小带宽不限流量」两种类型，前者的月流量用不完可以叠加到下个月，用完会被限速到 5Mbps；后者带宽小一些但不限量。n8n 这种场景的流量特征很分裂——平时几乎不动，某个工作流一旦开始传文件就爆量。个人用选限流量型、月流量几十 GB 那一档通常就够。

**第二步，解析域名。** 在 DNS 服务商处加一条 A 记录，把 `flow.你的域名.com` 指向服务器公网 IP。用 `nslookup` 确认一下解析是否生效。

**第三步，放通端口。** 只开 22（SSH）、80（证书验证与跳转）、443（HTTPS）。n8n 自己的 5678 端口不要暴露到公网，让它只在本机监听，由反向代理转发进来。

**第四步，写配置文件。** 新建目录，创建下面的 `compose.yaml`：

yaml
services:
  postgres:
    image: postgres:16-alpine
    restart: unless-stopped
    environment:
      POSTGRES_USER: n8n
      POSTGRES_PASSWORD: 换成你自己的强密码
      POSTGRES_DB: n8n
    volumes:
      - pg-data:/var/lib/postgresql/data

  n8n:
    image: docker.n8n.io/n8nio/n8n
    restart: unless-stopped
    ports:
      - "127.0.0.1:5678:5678"
    environment:
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: 换成你自己的强密码
      DB_POSTGRESDB_DATABASE: n8n
      N8N_HOST: flow.你的域名.com
      N8N_PROTOCOL: https
      N8N_PORT: 5678
      WEBHOOK_URL: https://flow.你的域名.com/
      N8N_ENCRYPTION_KEY: 换成一串随机长字符串
      GENERIC_TIMEZONE: Asia/Shanghai
      TZ: Asia/Shanghai
    volumes:
      - n8n-data:/home/node/.n8n
    depends_on:
      - postgres

volumes:
  pg-data:
  n8n-data:


再写一个 `Caddyfile`，Caddy 会自动申请并续期 Let's Encrypt 证书：


flow.你的域名.com {
    reverse_proxy 127.0.0.1:5678
}


**第五步，启动。** 在目录下执行 `docker compose up -d`，用 `docker compose logs -f n8n` 看日志，等到容器正常起来。

**第六步，创建账号。** 浏览器打开你的域名，会提示创建第一个账号。这个账号是实例的所有者，等于超级管理员，权限覆盖所有工作流和凭据。之后给同事用的账号要单独开普通成员级别，方便追溯改动。

## 三个最容易踩的坑

### WEBHOOK_URL 配置不对

这是自托管 n8n 最高频的故障。`N8N_HOST` 和 `WEBHOOK_URL` 如果没填对外访问的域名，n8n 生成出来的回调地址会带上容器内部的地址或端口，外部系统打过来直接 404。已建好的工作流在改了这两个变量之后，最好重新打开一次再保存。

### 直接用 IP 加端口访问

不配域名、直接开 `http://IP:5678`，n8n 会因为不是 HTTPS 弹 secure cookie 警告，登不进去。绕过办法是加 `N8N_SECURE_COOKIE=false`，但那只适合本机调试，公网实例别这么干——管理后台裸奔在 80 端口上，风险不用多说。

### N8N_ENCRYPTION_KEY 丢了

你在节点里存的第三方 API Key、数据库密码，都是用这个 key 加密后落盘的。key 丢了不是"重新登录一下"的事，那些凭据全部解不开，得一个个重新录入。生成一串足够随机的字符串，单独存一份。

## 备份：要备的是三样东西

很多人只备份了工作流导出的 JSON，真出事的时候发现恢复不完整。完整备份至少包括：

1. **Postgres 数据卷**（`pg-data`）：工作流定义、执行历史、用户账号。
2. **n8n 数据卷**（`n8n-data`）：包括容器内的配置和加密数据。
3. **N8N_ENCRYPTION_KEY**：没有它，上面两份数据里的凭据等于一堆乱码。

云服务器本身的分层快照能保底，但依赖快照就要承担和实例绑定的代价——实例丢了，快照也不好取。稳妥做法是定期把数据卷打包下载到本地或者对象存储。顺带一提，雨云除了云服务器还有对象存储产品，把备份丢在那儿是个省事的搭配。

## 常见问题

**n8n 自托管本身要花钱吗？**

软件本身不按执行次数收费，这是它相对托管服务的主要差异。实际成本就是服务器、域名和可能用到的 AI 模型 API 费用。

**1核1G 真的能跑吗？**

能启动，也能跑通几个简单工作流。但内存一旦被工作流吃满，容器会被 OOM 杀掉，表现是执行到一半莫名中断。省这十几块钱换来的是随时排查故障，不太划算。

**一定要域名吗？**

纯定时任务场景可以不要。但 Webhook、OAuth 回调、以及 n8n 的 secure cookie 机制都指向同一个结论：公网可访问的 HTTPS 域名是标配。

**升级配置时数据会丢吗？**

雨云后台支持扩容和套餐升级，但系统盘操作前记得先备份数据卷。养成先备份再动配置的习惯，比事后找快照要快。
